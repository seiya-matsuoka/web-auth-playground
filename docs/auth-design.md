# web-auth-playground 認証・認可設計

認証と認可の実装に使用する設計書である。
現時点の対象は、最初の一周で作る「登録 → ログイン → 本人情報の取得 → ログアウト」である。
後続機能を設計する際は、対象の節を追加し、影響する共通仕様も更新する。
学習目的、アプリ全体の要件、公開条件、追加候補は [開発計画](./project-plan.md) に記載する。

## 最初の一周の範囲

1 ページ（`/`）、4 本の API、2 テーブル（`accounts`、`sessions`）で、ブラウザ・API・DB をつないで動作を確認する。
アカウントを登録して学習用パスワードを受け取り、その値で明示的にログインする。
別のリクエストで本人情報を取得し、現在のセッションだけをログアウトで失効させる。
アカウントとセッションの通常の期限判定もこの一周で実装する。

本人によるアカウント削除、区分選択と区分別の認可、期限切れデータの定期削除は後続の実装単位とする。
同じブラウザでアカウントを切り替える場合は、ログアウトした後に別のアカウントでログインする。
最初の一周はローカルで検証し、公開は [開発計画の公開条件](./project-plan.md#公開する際に満たす条件) に沿って別途判断する。

## 画面遷移

URL は `/` とし、React の状態で表示を切り替える。
ブラウザから同一オリジンの `/api` を `fetch` で呼び出す。
登録結果のパスワードを一つのページ内で扱うことで、画面間で値を引き渡す処理を省ける。

| 場面                 | API と遷移                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 初回表示・再読み込み | 先に画面と「ログイン状態を確認中」の表示を出し、`GET /api/me` を呼ぶ。`200` なら本人情報、`401` ならログインフォームを表示する。通信エラーや `5xx` では再試行を案内する。 |
| 登録                 | ログイン画面から登録フォームへ切り替え、`POST /api/accounts` にユーザー名を送る。`201` で発行パスワードの確認画面に進み、`400` や `409` では入力を見直せるようにする。    |
| 発行パスワードの確認 | 発行されたパスワードを一度表示し、コピーしてからログインに進める。ログインフォームにはユーザー名だけを引き継ぐ。                                                          |
| ログイン             | 利用者がパスワードを入力し、`POST /api/login` を呼ぶ。`204` を受け取った後に `GET /api/me` を呼び、`200` なら本人情報を表示する。失敗時は結果を画面に伝える。             |
| 本人情報             | `GET /api/me` が返したユーザー名と、ログアウト操作を表示する。次の本人情報取得で `401` になった時点でログインフォームへ戻る。                                             |
| ログアウト           | `POST /api/logout` の `204` を確認してからログインフォームへ戻る。通信エラーや `5xx` では失敗を知らせ、再試行できるようにする。                                           |

登録結果のパスワードは確認画面の React の状態にだけ保持し、画面から離れたときに破棄する。
再読み込み後の再表示や、アプリによるブラウザの永続ストレージへの保存は行わない。
パスワードを失った場合は新しい学習用アカウントを登録する。
フォームでは学習用の値を使うことと、ユーザー名で大文字・小文字を区別することを案内する。
通信や DB のエラーは未ログインと区別し、画面を開いたまま期限に達したときは次の API 応答で表示を更新する。

### スタイリング

Tailwind CSS と CSS 変数を使用する。
背景色・文字色などの共通値と、フォームやボタンで共通に使うスタイルの定義を集約し、必要な画面や部品から参照する。
環境構築では Tailwind CSS が適用され、最小のトップページで共通値を参照できるところまで用意する。
認証フローの実装時は共通テーマ一つで、フォームの入力、処理中・成功・エラーの状態、ログイン状態の変化が分かる表示を用意する。
画面のレイアウトや区分ごとのテーマは、必要な画面と部品がそろった段階で調整する。
区分を追加する際は共通値を区分に応じて切り替え、区分名も画面に表示する。

## API の入出力

| API                  | リクエスト                                              | 成功時                                                                                                   | 主な失敗時                                                                                                 |
| -------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `POST /api/accounts` | JSON の `username`                                      | `201`。JSON で `username`、`password` を返す。`password` は発行した学習用パスワードである。              | `400` は入力不正、`409` は同じ名前の行が DB に存在する場合。                                               |
| `POST /api/login`    | JSON の `username`、`password`                          | `204`。新しいセッションを保存し、`Set-Cookie` を返す。                                                   | `400` は入力形式の不備。`401` は名前が存在しない、パスワードが一致しない、アカウントが期限切れのいずれか。 |
| `GET /api/me`        | セッション Cookie。ユーザー名や内部 ID は受け取らない。 | `200`。サーバーが特定した本人の `username` だけを JSON で返す。                                          | `401` は有効なセッションとアカウントを確認できない場合。                                                   |
| `POST /api/logout`   | セッション Cookie。リクエストボディは不要。             | `204`。現在のセッションを削除し、Cookie を消す。対象のセッションがすでに消えている場合も同じ応答とする。 | `5xx` は DB 障害などで失効処理を完了できない場合。                                                         |

- `204` のレスポンスボディは空とする。登録ではアカウント作成までを行い、ログインでセッションと Cookie を発行する。
- 登録とログインではサーバーで JSON の項目と型を検証する。ユーザー名は半角英数字（`A-Z`、`a-z`、`0-9`）の 3〜16 文字とし、大文字・小文字と入力時の表記をそのまま扱う。
- エラーは `{"error":{"code":"INVALID_CREDENTIALS"}}` のように、画面が機械的に判定できるコードを JSON で返す。日本語の表示文は画面側で決める。
- ログインの認証失敗は同じ `401` とエラーコードで返す。登録の `409` では利用者が名前を選び直せるようにするため、名前の使用状況を推測できる点は [公開条件](./project-plan.md#公開する際に満たす条件) で扱う。
- DB 障害や想定外のサーバーエラーは `5xx` とし、SQL や接続情報、認証情報などの内部情報を応答に含めない。

### HTTP と認証処理の責務

| 層                           | 担当する処理                                                                                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| React の画面                 | フォームから入力を受け取り、`fetch` で API を呼ぶ。応答に従って画面状態を変える。                                                                                |
| Next.js の Route Handler     | `route.ts` の `GET` または `POST` で HTTP を受け、ボディ・ヘッダー・Cookie を扱う。自前の関数を呼び、結果をステータス・ヘッダー・レスポンスボディに変換する。    |
| サーバー側の TypeScript 関数 | 登録と入力条件、パスワードの照合、セッションの発行・照合・期限判定・失効を扱う。Next.js 固有のリクエストやレスポンスのオブジェクトへの依存を HTTP の入口に置く。 |
| DB 処理                      | Postgres.js とパラメーター化した SQL で、必要な読み取り・書き込みを行う。制約による重複防止やアカウントとセッションの関連付けもここで扱う。                      |

サーバーは Node.js 上で動作し、認証の判断に必要な関数を自前で定義する。
たとえば `GET /api/me` では、Route Handler が `request.cookies.get('session')?.value` で照合用の値を読み、`verifySession` のようなサーバー側の共通関数を明示的に呼ぶ。
`request.cookies` は `NextRequest` から Cookie を名前で読むために使い、該当する Cookie がなければこの式の結果は `undefined` となる。
`verifySession` は処理の責務を示す名前の例である。
サーバー専用モジュールはクライアント側と分け、誤った読み込みを防ぐために `server-only` を利用できる。 [Next.js の Route Handler と Cookie](https://nextjs.org/docs/app/api-reference/file-conventions/route#cookies) · [サーバー専用モジュール](https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning)

## データベース

`accounts` は登録ごとに 1 行、`sessions` はログイン成功ごとに 1 行を持つ。
日時は `timestamptz` として保存し、サーバー側で現在時刻と比較する。
各列には値を必須とする。
区分の列は、登録時の区分選択と区分による認可を作る回で追加する。

### accounts

| 列              | 型・制約         | 内容                                                                 |
| --------------- | ---------------- | -------------------------------------------------------------------- |
| `id`            | `uuid`・主キー   | 登録時に発行する内部 ID。                                            |
| `username`      | `text`・`UNIQUE` | ログイン時に使う名前。大文字・小文字を区別する比較で一意にする。     |
| `password_hash` | `text`           | パスワード用のハッシュ。採用する方式に必要なソルトや設定情報を含む。 |
| `created_at`    | `timestamptz`    | 登録時刻。                                                           |
| `expires_at`    | `timestamptz`    | 登録から 24 時間後の利用期限。                                       |

`Sora7` と `sora7` は別アカウントとし、ログイン時の検索と一意性制約で同じ比較ルールを使う。
同時に登録された場合も、完全に同じ名前は DB の `UNIQUE` 制約で拒否する。
期限切れでも行が残っていれば同じ名前の登録は `409` とする。
削除後に同じ名前を再登録できる場合は、新しい内部 ID とパスワードを発行する。 [PostgreSQL の比較規則](https://www.postgresql.org/docs/current/collation.html#COLLATION-NONDETERMINISTIC) · [PostgreSQL の制約](https://www.postgresql.org/docs/current/ddl-constraints.html)

### sessions

| 列           | 型・制約                                                  | 内容                                                                                  |
| ------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `token_hash` | `text`・主キー                                            | Cookie で受け取る照合用の値を SHA-256 でハッシュ化したもの。                          |
| `account_id` | `uuid`・`accounts.id` への外部キー（`ON DELETE CASCADE`） | ログインしたアカウントの内部 ID。アカウントの物理削除時は関連セッションも削除される。 |
| `created_at` | `timestamptz`                                             | ログインに成功し、セッションを作った時刻。                                            |
| `expires_at` | `timestamptz`                                             | セッションを作ってから 1 時間後の有効期限。                                           |

セッションは名前ではなく内部 ID に関連付くため、削除前のセッションが同じ名前で再登録されたアカウントに結び付くことはない。
同じアカウントでもログインごとに独立したセッションを持つ。

### 登録・ログイン・失効の処理

1. **登録。** サーバーでユーザー名を検証し、安全な乱数からパスワードを発行してハッシュ化する。アカウントの挿入が成功してから発行パスワードを返す。重複の最終判断は DB の制約に任せ、同名の競合は `409` に変換する。
2. **ログイン。** ユーザー名で見つけたアカウントの期限とパスワードを照合する。照合の間はトランザクションを開いたままにせず、セッションを挿入する時点でも対象アカウントの存在と利用期限を確かめる。挿入に成功してから、新たに生成した照合用の値を Cookie として返す。
3. **本人情報の取得。** Cookie の値を使ってセッションとアカウントを照合する。両方が有効な場合だけ、該当アカウントのユーザー名を返す。この操作では DB を読み取る。
4. **ログアウト。** Cookie の値に対応する現在のセッション行を 1 回の DB 更新で削除し、ブラウザに Cookie の削除を指示する。対象の行や Cookie が存在しない場合もログアウト済みとして扱う。同じアカウントの別セッションは引き続き利用できる。

### セッションの有効性

セッションの存在と対応するアカウントの存在を照合し、`sessions.expires_at` と `accounts.expires_at` がともに現在時刻より後の場合に有効と判定する。
`expires_at` に達した時点で利用を拒否する。
操作や画面の再読み込みでどちらの期限も延長しない。
セッションだけが期限切れの場合は、アカウントが有効な間は再ログインできる。
アカウントが期限切れの場合は、残り時間のあるセッションも含め、そのアカウントの全セッションと新規ログインを拒否する。

時間の経過による失効は読み取り時に判定する。
DB の不要行を実際に削除する定期処理は、公開前に別途用意する。
ログアウトによる現在のセッション行の削除と、期限による利用拒否は、それぞれ独立して確認する。

## パスワード・Cookie・リクエスト保護

### パスワードとセッションの照合用の値

パスワードとセッションの照合用の値は、サーバー側で Node.js の暗号学的に安全な乱数生成を使い、それぞれ独立して生成する。
パスワードは既存の実装を用いて Argon2id でハッシュ化する方針とし、Node.js の `argon2` パッケージを第一候補とする。
実行環境に適合しない場合は、Node.js 標準の `scrypt` などを比較する。
DB に保存するのは照合に必要なハッシュで、平文のパスワードを返すのは登録成功時の一度だけとする。

セッションは推測困難なランダム値をブラウザの Cookie に渡し、DB には SHA-256 のハッシュを保存する。
リクエストで受け取った値も同じ方法でハッシュ化して照合する。
パスワード用のハッシュはパスワードの推測にかかる計算量を上げ、セッションのハッシュは高エントロピーな値を DB で照合するために使う。 [Node.js の乱数生成](https://nodejs.org/api/crypto.html#cryptorandombytessize-callback) · [OWASP のパスワード保存](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

### Cookie の受け渡し

ログイン成功時にサーバーが `Set-Cookie` を返し、ブラウザは条件を満たす後続のリクエストに `Cookie` ヘッダーを付ける。
このヘッダーはボディや URL のパラメーターと独立している。
Web 標準の `request.headers.get('cookie')` でヘッダー全体を読める。
値の取り出し方は使用するフレームワークの HTTP API に従い、受け取った値を DB で照合する部分はサーバー側の共通関数で扱う。
Cookie の値はセッションを照合するための値だけとし、ユーザー名や区分は含めない。
値の受け渡しはブラウザとサーバーに任せ、画面の JavaScript から API の JSON や `localStorage` にコピーしない。

| 項目       | 設定                                                                                                                  |
| ---------- | --------------------------------------------------------------------------------------------------------------------- |
| `HttpOnly` | 設定する。                                                                                                            |
| `SameSite` | `Lax` を設定する。                                                                                                    |
| `Path`     | `/` とする。                                                                                                          |
| `Domain`   | 指定せずホスト単位とする。                                                                                            |
| `Secure`   | 公開 HTTPS 環境で設定する。開発用のローカル HTTP の場合だけ設定を分ける。                                             |
| 有効期限   | ブラウザでの保持とは別に、DB の有効期限をサーバーで判定する。ログアウト成功時は同じ名前・パスの Cookie を失効させる。 |

Cookie がブラウザに残っていても、DB で有効なセッションとアカウントを確認できない場合は認証済みとして扱わない。 [Set-Cookie の属性](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) · [OWASP のセッション管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### オリジン・キャッシュ・ログ

- 登録・ログイン・ログアウトの `POST` では、`Origin` ヘッダーを事前に設定した自アプリのオリジン（スキーム・ホスト・ポート）とサーバー側で照合する。欠落や不一致は `403` で拒否し、DB の更新や Cookie の設定に進めない。
- 発行パスワード、ログイン・ログアウト結果、本人情報などを扱う応答には `Cache-Control: no-store` を設定する。
- パスワード、セッションの照合用の値、DB の接続情報を URL やアプリのログに含めない。入力値やリクエスト・レスポンス全体の記録も避ける。
- 登録・ログインの連続試行への対策など、公開環境で満たす条件は [開発計画](./project-plan.md#公開する際に満たす条件) で追跡する。

[OWASP の CSRF 対策](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#using-standard-headers-to-verify-origin) · [OWASP のログに残さない情報](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)

## ローカルでの確認方法

[環境構築](./project-plan.md#環境構築) で用意した Node.js 上の Next.js と、Docker Compose のプロジェクト専用 PostgreSQL を使う。
DB のポート公開先はループバックアドレスとし、接続情報はサーバー側の `DATABASE_URL` で扱う。
ローカルの開発・検証用 DB を公開環境の DB と分け、空の DB に同じ SQL からテーブルと制約を再現できるようにする。

### ブラウザでの確認

- 登録、発行パスワードの表示とコピー、ログイン、本人情報の表示、再読み込み、ログアウトを通す。
  登録結果からログインへ進む際に名前だけが引き継がれ、結果画面を離れた後や再読み込み後にパスワードを再表示できないことも確認する。
- Network タブでログイン成功時の `204` と `Set-Cookie`、続く `GET /api/me` の `Cookie` ヘッダーと `200`、ログアウト後の `GET /api/me` の `401` を確認する。
  Cookie の値そのものを検証記録に残す必要はない。
- Cookie を共有しない二つのブラウザ環境で同じアカウントにログインし、片方のログアウト後にもう片方で本人情報を取得できることを確認する。
- `401` でログインフォームに戻る表示と、通信エラーやサーバーエラーで再試行を案内する表示を確認する。

### API と DB での確認

| 観点                 | 確認すること                                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 入力と重複           | `Sora7` の登録は `201`、同名は `409`、`sora7` は別名として `201`。形式不正は `400` で行が増えない。ログイン時に `sora7` と `Sora7` のパスワードを組み合わせると `401` になる。 |
| パスワードとログイン | DB に平文が保存されず、正しいパスワードでのみセッションが作られる。名前がない場合と間違ったパスワードの場合は同じ `401` で、セッション行が増えない。                           |
| セッション照合       | 未ログインや無効な Cookie の `GET /api/me` は `401`。有効な場合は本人のユーザー名だけを返す。照合や再読み込みで期限が延長されない。                                            |
| ログアウト           | 該当するセッション行だけが消える。別セッションやアカウントは引き続き有効で、同じログアウト操作を繰り返しても `204` になる。                                                    |
| セッション期限       | アカウントが有効でセッションだけ期限切れのとき、Cookie が残っていても `GET /api/me` は `401`。同じパスワードで再ログインできる。                                               |
| アカウント期限       | アカウントだけが期限切れのとき、どのセッションからの `GET /api/me` も `401` になる。正しいパスワードでの新規ログインも同じ `401` になり、行が残る間は同名で登録できない。      |
| オリジン・キャッシュ | `Origin` が欠落または不一致の `POST` は `403` で、状態が変わらない。対象の応答には `Cache-Control: no-store` が付く。                                                          |
| DB のエラー          | `GET /api/me` で DB から結果を得られない場合は `5xx` となる。ログアウトの失効処理に失敗した場合も `5xx` となり、画面は成功を表示せず再試行を案内する。                         |

期限のケースは、検証専用のローカル DB でセッションだけ、またはアカウントだけの期限を過去にしたデータを使う。
Cookie が残る状態で API を呼び、通常のサーバー側の期限判定を通して確認する。
実時間で待たずに確認でき、利用者向けの強制期限切れ操作は追加候補として別に扱う。
本人情報が返るかどうかを画面だけで判断せず、HTTP の応答と DB の行の変化を照合し、判断を担うコードも確認する。

## 実装時に確定する詳細

- 学習用パスワードの文字種・長さ・形式、およびログイン時に形式をどこまで検証するかを決める。
- ハッシュライブラリの適合性・バージョン・パラメーター、セッションの照合用の値のエンコード、Cookie の保持期間の設定を確認する。
- エラーコードと画面文言の細部、ファイル・関数の具体名、SQL の配置と実行手順は、実装に必要な粒度で確定する。
