# web-auth-playground 開発計画

この文書は、企画・要件・仕様・設計について、現時点の合意と今後の検討事項をまとめる開発中の計画である。
実装と動作確認で分かったことを反映し、現在の方針が分かるように更新する。
採用候補と未決事項は、実装を約束した機能と区別する。
大きな判断を変えたときは、変更前・変更後・理由をこの文書に短く残す。
完成後に残す企画・要件・仕様・設計の文書は、実際に実装した内容と確認結果を基準に整理する。

## 企画と進め方

Web の認証・セッション管理・認可の基礎を、自分で設計し、実装し、動作を確かめるための個人開発アプリを作る。
アカウントを登録し、ログイン状態や区分によって、同じ画面や操作の結果がどう変わるかを試せるようにする。
アカウントの操作と確認用の小さな機能に絞り、投稿や商品管理などの別の業務機能は設けない。
リポジトリ名は `web-auth-playground` とする。
学習課題の集積ではなく、ブラウザで認証・認可を試せるアプリであることを名前に表す。

| 学ぶこと       | アプリで確かめること                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 認証           | ユーザー名でアカウントを特定し、発行されたパスワードを根拠にログインを認める条件               |
| セッション管理 | HTTP リクエストをまたいで本人を識別し、ログアウトや期限切れでログイン状態を終わらせる方法      |
| 認可           | ログインしている人に、対象の情報を返したり操作を実行したりしてよいかをサーバー側で判断する方法 |
| アカウント管理 | 登録、利用期限、削除と、それにひも付くセッションの扱い                                         |

GitHub にコードを公開し、アプリもデプロイする。
ホスティングと DB は、個人開発として無料枠で利用できる構成を前提に選ぶ。
公開の目的は学習成果を試せるようにすることであり、継続利用を前提とした会員サービスは想定しない。
主な利用者は開発者自身で、第三者が操作する場合も日をまたいで同じアカウントを使う場面はほとんど想定しない。
入力・保存する情報を絞り、公開環境の認証・認可とセッション管理はサーバー側で実際に機能させる。

全体の方針と直近の範囲を決め、小さな単位で設計、実装、確認を繰り返す。
各回は、必要な範囲で画面から API と DB までをつなぎ、成功と拒否の両方を操作・通信・コードから確かめる。
実装や検証が済んだことと、学習者が自分で操作して仕組みを理解できたことは区別して扱う。
その結果から、次に作る機能や候補の優先順位を見直す。
厳密なアジャイルの手順や固定の期間は設けず、個人開発の規模に合わせる。
公開時期は各回の完了から切り離し、公開する機能と必要な保護がそろった時点で判断する。

## 合意した要件・仕様

### 登録とアカウント

- 利用者が登録フォームでユーザー名を入力し、登録する。
  入力したユーザー名は、その後のログインにも使う。
- ユーザー名は半角英数字（`A-Z`、`a-z`、`0-9`）の 3〜16 文字とし、大文字・小文字を区別する。
  入力した表記を保存・表示し、登録とログインで同じ比較ルールを使う。
  空白、記号、日本語は初期の許可範囲に含めない。
- 完全に同じユーザー名を重複登録できないようにする。
  `Sora7` と `sora7` は別の名前として扱う。
  アカウントを削除した後は同じ名前を再利用できるが、別の内部 ID と新しいパスワードを持つ新規アカウントになる。
  期限を過ぎても DB に行が残っている間は、削除されるまでその名前を再利用できない方針とする。
- パスワードは登録時にサーバーが学習専用のものを発行し、登録結果で一度だけ表示する。
  登録フォームで利用者が普段使うパスワードを指定する場面をなくしつつ、発行されたパスワードを入力してログインする体験を残す。
  発行したパスワードの再表示、再設定、復旧は設けず、紛失時は別のアカウントを作る。
- 氏名、メールアドレス、電話番号などを登録項目に含めない。
  ユーザー名の文字種や長さだけで実名などの入力を防ぎ切ることはできないため、学習用の名前を使うよう画面で案内する。
- アカウントの利用期限は登録から **24 時間**とし、操作のたびには延長しない。
  期限に達したアカウントは、ログインも、既存セッションからの操作もできない。
- 自分のアカウント情報を閲覧・削除できるようにする。
  他のアカウントの情報は閲覧・削除できない。
  アカウントが削除されたら、そのアカウントにひも付く全セッションから操作できなくなる。

### ログイン状態と期限

- ログインでは、ユーザー名でアカウントを特定し、アカウントの利用期限とパスワードを確認する。
  成功するたびに新しいセッションを作り、ブラウザに照合用の値を Cookie で渡す。
- セッションの有効期限はログインから **1 時間**とし、操作や再読み込みで延長しない。
  セッションだけが期限切れなら、アカウントの有効期間内は同じパスワードで再ログインできる。
- 保護する操作では、サーバーがセッションとアカウントの両方が有効かを確認する。
  Cookie が残っていても、期限切れ・失効・削除などで利用できない場合は認証済みとして扱わない。
- 通常のログアウトでは、今使っているセッションだけを DB 側で無効にし、そのブラウザの Cookie を消す。
  同じアカウントで別のブラウザから作ったセッションは継続する。
  アカウントそのものが期限切れ、または削除された場合は、全セッションに影響する。
- **利用を止めることと、DB から削除することを分ける。**
  期限は DB に時刻として保存し、サーバーがログインや保護された操作の際に判定する。
  期限に達した瞬間に DB の行を書き換える必要はなく、削除処理がまだ走っていなくても利用を拒否できる。
  期限切れのアカウントと不要なセッションを自動的に削除する仕組みは、公開前に用意する。
- 初回の画面では、期限に達した瞬間に表示を切り替える必要はない。
  次の操作や再読み込みで保護された API が `401` を返したら、未ログインの表示に戻す。

### 所有者とアカウント区分による認可

- **自分のものか**という認可は、本人情報の閲覧や削除を通じて扱う。
  対象は、サーバーが確認したセッションにひも付くアカウントを基準に決める。
- **どの区分に属するか**という認可も、全体の学習範囲に含める。
  登録時に用意された学習用区分から一つを選び、ログイン後の操作ではサーバーが管理する区分を根拠に許可・拒否する。
  区分はまず二つを想定し、名称や各区分で試せる操作は該当する回で決める。
- 区分は学習用のデータや操作にだけ影響する。
  どの区分でも、他人のアカウントの管理や、サーバー・DB の管理はできない。
- 区分ごとに非表示または無効になるボタンと、どの区分でも押せるがサーバーで許可・拒否が分かれるボタンを設ける方向とする。
  前者も、表示の制御とは別にサーバー側で保護する。
  後者では、画面上は操作できても、条件を満たさなければサーバーが拒否することを観察できる。
- 画面構成は区分間でそろえ、テーマカラーをはっきり変えて、現在の区分を見分けられるようにする。
  区分名、アイコン、表示文言なども、必要に応じて違いを表す候補とする。
  画面の違いは利用者への案内であり、認可は API で実施する。

## 技術構成と責務

- **採用する構成:** Next.js App Router と TypeScript を使い、画面は React、バックエンドは Node.js 上で動く Route Handler とサーバー側の TypeScript モジュールで構成する。
- **公開先と DB の想定:** 画面と API は Vercel の同じ公開オリジン、公開環境の DB は Neon PostgreSQL を第一候補とする。
  React の画面から同一オリジンの `/api` を `fetch` で呼び、ブラウザの Network タブで通信を追えるようにする。
  公開する画面では、共通の画面を先に表示し、API が返るまで待機中であることを伝えられる構成を想定する。
- **Next.js に任せる処理:** 画面・API のルーティング、HTTP リクエストの読み取り、Cookie の取得・設定、レスポンスの組み立てに既存の API を使う。
  `route.ts` の `GET` や `POST` が入口となり、そこからサーバー側の関数を呼ぶ。
- **自分で設計・実装する処理:** 登録条件、パスワードの生成・保存・照合の流れ、セッションの作成・照合・期限判定・失効、所有者や区分による認可を扱う。
  たとえば `login` や `verifySession` は自分で定義する関数であり、Next.js の機能ではない。
  関数名やファイル名は設計時に決める。
- **既存の基礎部品を使う処理:** 安全な乱数生成には Node.js の標準 API、パスワードの保存・照合には適切なパスワード用ハッシュの既存実装、DB 接続にはドライバーを使う。
  認証サービスに処理一式を任せる方式は、判断の流れを自分で書くという今回の目的から初期構成に採用しない。
  ハッシュ方式は Argon2id を第一候補とし、実行環境に合わなければ Node.js 標準の `scrypt` などを比較する。
  DB アクセスは、既存の経験がある Postgres.js とパラメーター化した SQL を候補とする。

サーバー側の処理は `route.ts` にまとめず、認証・セッション・DB の処理を必要に応じて通常の TypeScript モジュールに分ける。
保護する Route Handler は共通の確認処理を明示的に呼び、操作ごとの権限を確認してからデータを返す。
Express ではルート群のミドルウェアから共通チェックを呼べる。
今回の Next.js 構成では、認証が必要な Route Handler から共通関数を呼ぶことで、どの操作を保護するかをコードで追えるようにする。
Cookie の読み書きや HTTP の入出力を入口側に置くと、認証の中核は Next.js 固有のオブジェクトに依存しない。
サーバー専用モジュールの誤った `import` を防ぐ方法として `server-only` を利用できる。
具体的なディレクトリ構成は、最初の実装に必要な分だけ決める。

### Cookie と DB の役割

ログイン成功時は、サーバーが生成した推測困難な値を `Set-Cookie` レスポンスヘッダーで渡す。
ブラウザは条件を満たす後続リクエストの `Cookie` ヘッダーにその値を付ける。
画面側で Cookie の値を取り出し、ボディや URL に入れて送る必要はない。
Route Handler では、Web 標準の `request.headers.get('cookie')` でヘッダー全体を読める。
Next.js の `request.cookies.get('session')?.value` は、指定した名前の値だけを取り出す例で、該当する Cookie がなければ `undefined` になる。
取り出した値をセッション確認関数の引数として渡す。
ヘッダーから値を取り出す書き方はフレームワークによって異なるが、値を DB で照合して本人を判定する考え方は共通である。

Cookie の値には、ユーザー名や区分を含めない。
セッションの値は API の JSON や `localStorage` に重複して保存しない。
DB にはアカウントとの関連、有効期限、照合用の値のハッシュを保存する。
受信した値を同じ方法でハッシュ化し、DB に保存した値と照合する。
ランダムなセッション値を DB で照合するためのハッシュと、パスワードを安全に保存するためのハッシュは、用途を分けて考える。
セッションは DB にあるため、アプリサーバーの再起動や実行環境の切り替わりで失われるメモリに依存しない。

関連資料: [Next.js の Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)、[Next.js のプロジェクト構成](https://nextjs.org/docs/app/getting-started/project-structure)、[Route Handler の Cookie 操作](https://nextjs.org/docs/app/api-reference/file-conventions/route#cookies)、[サーバー専用モジュール](https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning)、[OWASP のセッション管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[OWASP のパスワード保存](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

## 最初の一周

**登録 → ログイン → 本人情報の取得 → ログアウト**をローカルでつなげる。
画面には、登録フォーム、発行パスワードの確認、ログインフォーム、本人情報とログアウト操作を用意する。
別ページと同一ページ内の切り替えのどちらにするかは、画面設計で決める。
登録後は自動ログインせず、発行されたパスワードであらためてログインする。

| 操作           | API の設計案         | サーバー側の処理と結果                                                                                               |
| -------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 登録           | `POST /api/accounts` | ユーザー名を検証してアカウントを登録し、成功時だけ発行したパスワードを一度返す                                       |
| ログイン       | `POST /api/login`    | ユーザー名とパスワードを受け取り、アカウントの期限とパスワードを確認し、成功時にセッションを作って Cookie を設定する |
| 本人情報の取得 | `GET /api/me`        | 対象のユーザー名や ID は受け取らず、Cookie の照合で特定した本人のユーザー名を返す。認証が成立しなければ `401` を返す |
| ログアウト     | `POST /api/logout`   | 今使っているセッションを無効にし、ブラウザの Cookie を消す。初回はセッション行の削除を基本案とする                   |

| DB の保存対象 | 最初に必要な情報                                                                       |
| ------------- | -------------------------------------------------------------------------------------- |
| アカウント    | 内部 ID、ユーザー名、パスワードのハッシュ、アカウントの利用期限                        |
| セッション    | Cookie の値を照合するためのハッシュ、対応するアカウントの内部 ID、セッションの有効期限 |

アカウントの内部 ID は、ログインに使うユーザー名と分ける。
DB でも大文字・小文字を区別する比較でユーザー名に一意性を持たせ、セッションを内部 ID に関連付ける。
同じ名前で登録し直しても、古いセッションが新しいアカウントに結び付くことはない。
ログイン・ログアウトは DB を更新するが、再読み込み時の照合や期限の判定は読み取りで済む。
区分の保存は、登録時の区分選択と区分による認可を作る回で追加できる。
[PostgreSQL の比較規則](https://www.postgresql.org/docs/current/collation.html#COLLATION-NONDETERMINISTIC)、[DB の一意性・主キー・外部キーの制約](https://www.postgresql.org/docs/current/ddl-constraints.html)。

### 動作確認の条件

| 観点                   | 確認すること                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 登録・重複             | `Sora7` を登録でき、同じ `Sora7` は重複として拒否され、`sora7` は別の名前として扱われる                                               |
| パスワード             | 登録結果で発行した値を受け取れる。平文を DB に保存せず、正しいパスワードでのみログインが成立する                                      |
| セッションの作成と確認 | ログイン成功時に Cookie が発行され、再読み込みしても `GET /api/me` が本人のユーザー名を返す。誤ったパスワードではセッションを作らない |
| 未ログイン・ログアウト | 未ログインなら `401`。ログアウト後も `401` となり、サーバー側でも現在のセッションが無効になっている                                   |
| セッション期限         | 期限切れなら `401`。アカウントが有効な間は、同じパスワードで再ログインできる                                                          |
| 複数のセッション       | 同じアカウントで独立したブラウザセッションからログインし、一方のログアウトが他方に影響しない                                          |
| アカウント期限         | 期限切れになったアカウントは既存のどのセッションでも保護された操作ができず、正しいパスワードでも新たにログインできない                |

期限は短い設定や期限切れのテストデータを使い、実時間で 1 時間や 24 時間待たずに確認する。
開発時の確認方法と、利用者が操作できる強制期限切れボタンは別に扱う。
初回の結果を見て、本人によるアカウント削除と区分による認可のどちらに次に取り組むかを決める。

## 公開する際に満たす条件

アカウントや操作は学習用だが、実際に公開する機能は、以下の条件を満たすよう設計・確認する。
各機能の保護はその機能を設計する段階で扱い、公開の判断は実装の進み方と分ける。

- 公開時は HTTPS とし、セッション Cookie の `Secure`、`HttpOnly`、`SameSite` などを適切に設定する。
  Cookie の有無だけでなく、サーバーでセッションの有効性、アカウントの有効性、操作ごとの権限を確認する。
- 入力は画面とサーバーで検証し、サーバーで許可した項目と値だけを処理・保存する。
  区分などの固定の選択肢もサーバー側で確認する。
  画面で拒否すること、サーバーに届かないこと、DB に保存しないことはそれぞれ異なる。
- パスワードやセッション値を URL・アプリのログに含めず、入力値やリクエスト・レスポンス全体も不用意に記録しない。
  パスワードの発行結果や認証済みの本人情報を返すレスポンスなどは `Cache-Control: no-store` とし、ブラウザや共有キャッシュでの再利用を避ける。
  発行されたパスワードを画面で確認するために表示しても、アプリはブラウザの永続ストレージへ保存しない。
  公開リポジトリ、画面用のビルド、公開する検証記録に、認証情報や DB 接続情報などの秘密を含めない。
- 同一オリジンでも、Cookie を使う状態変更には CSRF 対策を用意する。
  公開前に、登録・ログインの連続試行への対策と、ログイン失敗時にアカウントの存在を不用意に知らせない応答も確認する。
- 期限切れのアカウントと、不要になったセッションを定期的に削除し、データが増え続けないようにする。
  サーバープロセス内の常駐タイマーだけに頼らず、Web アプリのプロセスとは別に動く定期処理などを検討する。
  DB からの物理的な削除が遅れても、サーバー側の期限判定で期限切れのアカウントは使えない。

公開された入力欄に利用者が実名や他サービスで使うパスワードを入れる可能性は残る。
学習専用のデータを使うよう案内し、不要な入力欄を用意しないことと、アプリが受け取る・保存する・記録する情報を制限することを組み合わせる。
ログイン時に発行済みパスワードの形式を検証することも候補とするが、形式検証だけで個人情報や他サービスのパスワードの送信がなくなるわけではない。
アプリが通常の操作で何を送信・保存しないかは検証できるが、ブラウザの入力中のメモリ、フォーム復元、拡張機能、ホスティング側のログ、画面を経由しない任意のリクエストまで含め、情報がどこにも残らないとは保証しない。

関連資料: [OWASP の入力検証](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)、[認証と連続試行への対策](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[認可](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)、[CSRF 対策](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)、[ログから除外するデータ](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)。

## 比較した案と選択理由

| 検討したこと                      | 比較と、今回の判断                                                                                                                                                                                                                                                                                                               |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ブラウザ内だけの疑似実装          | 構成が小さく、ブラウザ内の画面・仮想サーバー・仮想 DB に役割を分ければ処理の流れを体験できる。ただし、その分割は実際のサーバーと同じ保護を提供しない。実際の HTTP、サーバーとブラウザの信頼の境界、サーバーによる認可も学ぶため、今回はバックエンドを採用する。学習時だけ実サーバーを動かし、公開は疑似デモにする案も検討した    |
| バックエンドの一時データ・永続 DB | メモリに置くと実際のサーバー側判定は試せるが、停止・再起動後も別のリクエストから同じ状態を参照するには共有の保存先が必要になる。今回はアカウントとセッションを DB で管理し、保持するデータを絞って期限を設ける。保持期間、ブラウザ内の保存先、自動リセットは、ブラウザのみの案でも決める必要があった                             |
| ユーザー名と登録体験              | 自由入力した名前をログインに使う案、表示名をブラウザだけで使い別の発行 ID を控える案、用意された架空の名前を選ぶ案を比較した。架空の名前の選択は持ち込まれるデータを減らせるが、その制限はサーバー側でも必要になる。今回は指定した名前をそのままログインに使えるよう、短い任意入力とサーバー検証を採用する                       |
| 入力の破棄・置き換え・ハッシュ化  | 入力を破棄する場合は、その入力した名前で後からログインできない。入力と無関係な値を送る案は入力値の送信を避けられるが、別のログイン ID の受け渡しが必要になる。名前のような入力から作ったハッシュは候補の照合や関連付けが可能なため、匿名化の手段として採用しない                                                                 |
| パスワードの決め方                | 利用者が決める方式とアプリが発行する方式のどちらでも保存と照合を学べる。登録時に外部で使うパスワードを指定させないよう、今回はアプリが発行する。ユーザー名だけでの切り替えは、本人確認を学ぶ目的には足りない                                                                                                                     |
| バックエンドとフレームワーク      | React＋Vite と TypeScript／JavaScript＋Node.js＋Express、および Java＋Spring Boot を比較した。Express は API の入口と処理を追いやすい。今回は Next.js の Route Handler でもその境界を作れ、React と TypeScript の画面・API を一つのアプリとして扱えるため採用する。Python は今回の候補に含めない                                 |
| ログイン状態の持ち方              | Cookie はブラウザとサーバーの間で値を受け渡す仕組みで、JWT は値に使える形式の一つである。署名付き JWT に情報を持たせる方法もある。DB を参照せず署名と期限だけで判断する方式では、期限前の失効に別の仕組みが必要になる。今回はログアウト、失効、複数セッションを学ぶため、Cookie でランダムな値を送り DB で照合する方式を採用する |

技術選定では、今回と同じ用途で一般的に使われる方法や公式ガイドの推奨を優先する。
学習目的や扱うデータ、公開環境の制約から別の方法を選ぶときは、何を簡略化したかと理由を残す。
技術の参考にした過去の個人開発は、React・Express の [reading-log-app](https://github.com/seiya-matsuoka/reading-log-app)、Next.js・Neon の [football-moment-archive](https://github.com/seiya-matsuoka/football-moment-archive)、React・TypeScript・Vite の [random-cool-color-generator](https://github.com/seiya-matsuoka/random-cool-color-generator) である。

### 公開先・オリジンの比較

デプロイの単位と、ブラウザから見たオリジンは別である。
オリジンは通信方式、ホスト名、ポートで決まる。
別々の公開 URL にブラウザから直接アクセスすればクロスオリジンになり、画面側の `/api` で別サービスへの転送を受け持てば、配置を分けてもブラウザからは同一オリジンにできる。
今回は同一オリジンの HTTP API とし、別オリジンへ Cookie を付けて通信するための CORS 設定を学習の前提にしない。
[オリジンの定義](https://developer.mozilla.org/ja/docs/Glossary/Origin)、[Vercel の転送設定](https://vercel.com/docs/routing/rewrites#rewrites-to-external-origins)。

| 候補                                | 比較して分かったこと                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Render の Web Service＋Express      | 起動コマンドで Node.js を起動し、Express がポートで待ち受ける。React の画面ファイルも同じ Express から配る場合、停止後の初回はアプリの画面も起動を待つ。Render の待機ページと、アプリ独自の待機表示は別。静的サイトと API を分けることもできる                                                                                                        |
| Vercel の静的配信＋Express Function | Express のルートや認証・認可の中核はおおむね共通にできる。Vercel がリクエストに応じて Express を Function として稼働させる。Express の API を一つずつ Vercel 向けに書き直す必要はなく、起動・入口の規約と静的ファイルの配置が主に変わる。Vite の成果物を静的配信し `/api` を Express に届ける設定が必要で、Express の静的配信をそのまま使う形ではない |
| Next.js＋Vercel                     | 画面と Route Handlers を同じアプリに置ける。Express を別に設けなくても、画面から HTTP API を明示的に呼べる。共通の画面と動的な API を分けて配信でき、Vite の成果物と Express を組み合わせる設定を省けるため第一候補                                                                                                                                   |
| Cloudflare Workers                  | 無料枠の候補として比較した。リクエストあたりの CPU 制限とパスワード用ハッシュの負荷との相性を確認する必要があり、初期構成では優先しない                                                                                                                                                                                                               |

今回の認証・認可には常駐サーバーは必要ない。
Next.js 自体は、必要なら Node.js のサーバーとして常駐させることもできる。
Vercel でも Function の初回起動や Neon の休止後の復帰による API の待ち時間はあり得る。
静的な画面を先に配信して待機中の案内を出すことと、API の起動待ちがなくなることは別である。
旧 Vercel Postgres の新規提供はなく、Vercel で PostgreSQL を連携する場合は Neon などの外部サービスを利用する。
Render の無料 Web Service の停止条件、Render 無料 Postgres の利用期限、Neon の休止条件などは、実際に使う時点で再確認する。

関連資料: [Render の無料枠](https://render.com/docs/free)、[Vercel の Express 配置](https://vercel.com/docs/frameworks/backend/express)、[Vercel Functions の実行方式](https://vercel.com/docs/functions#how-the-vercel-functions-lifecycle-works)、[Vercel の Next.js 配置](https://vercel.com/docs/frameworks/full-stack/nextjs)、[Next.js のセルフホスティング](https://nextjs.org/docs/app/guides/self-hosting)、[Vercel の PostgreSQL 連携](https://vercel.com/docs/postgres)、[Neon の休止・再開](https://neon.com/docs/introduction/scale-to-zero)、[Cloudflare Workers の制限](https://developers.cloudflare.com/workers/platform/limits/)。
